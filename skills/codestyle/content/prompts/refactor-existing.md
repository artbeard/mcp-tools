# Рефакторинг существующего кода

Сценарий: правишь существующий код, не пишешь новую фичу с нуля.

## Принципы scope-discipline (MUST)

- Меняй ТОЛЬКО то, что относится к задаче. Не трогай файлы вне scope, даже если видишь «улучшения».
- Дублирование как tech-debt допустимо — лучше дублирование, чем выход за scope.
- Если по пути нашёл реальный баг — отдельным MR, не в текущей правке.

## Обязательные правила (URI) перед рефакторингом

- `codestyle://general/formatting` — табы, Allman (если форматируешь старый код в новый стиль)
- `codestyle://general/naming` — соглашения именования

## По типу рефакторинга

| Что меняешь | URI правил |
|---|---|
| Контроллер | `codestyle://backend/controller` + `codestyle://backend/dto` |
| Сервис | `codestyle://backend/service` |
| Entity | `codestyle://backend/entity` |
| Vue-компонент | `codestyle://frontend/component` |
| Pinia store | `codestyle://frontend/store` |
| API-вызовы | `codestyle://frontend/api-layer` |

## Чек-лист

- [ ] Изменения локализованы — затронуты только файлы, относящиеся к задаче.
- [ ] Не добавлены feature-флаги, backwards-compatibility shims, fallback'и для невозможных случаев.
- [ ] Если код был K&R — переводишь в Allman ТОЛЬКО трогаемые блоки, не весь файл.
- [ ] Старый стиль не разрешает поломать новые MUST-правила (например, нельзя оставить `Options API`, если файл переписывается).
- [ ] Удалены неиспользуемые импорты, переменные, dead code в зоне правок.
- [ ] Никаких комментариев типа `// removed X`, `// for backwards-compat`, `// TODO: refactor later` — либо делаем, либо нет.
