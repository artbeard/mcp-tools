# Правила ревью

Применяй эти правила только когда diff MR даёт конкретное evidence.

## Приоритеты

- `BLOCKER`: нельзя merge; security, небезопасная миграция, потеря данных, сломанный API-контракт, deploy-breaking код.
- `MAJOR`: нужно исправить до merge; корректность, архитектура, отсутствие обязательных тестов, performance-риск.
- `MINOR`: валидная проблема с узким scope (мало затронутых мест / низкий риск).
- `NIT`: явная style/cosmetic проблема.

## Scope

- Diff должен соответствовать описанию MR и опциональной задаче Tracker.
- Нерелевантные изменения поведения помечай как `MAJOR`.
- Нерелевантные рискованные миграции, security-изменения или production config помечай как `BLOCKER`.

## Направление Git-веток

- Рабочие ветки должны начинаться только от `master` или `main`; `dev` - downstream-ветка для демонстрации и тестирования.
- Разрешено только task → dev и master/main → dev. Запрещено dev → task, dev → master и dev → main.
- Для MR в `master`/`main` source `dev` или merge-коммиты из истории `dev` вне target являются `BLOCKER`.
- Конкретное evidence: source branch, merge-коммит `dev`/`into dev`, посторонние task-коммиты и изменённый файл из загрязнённого diff.
- Fix: пересобрать source от актуального remote target и перенести только явно выбранные task-коммиты; не merge/rebase/cherry-pick ветку `dev` целиком.

## Backend API

- Controller должен быть тонким и делегировать бизнес-логику в service.
- Controller должен возвращать данные напрямую через `$this->json($data, Response::HTTP_*)`.
- Не оборачивай API-ответы в `success`, `status`, `ok` или `data`, если существующий контракт endpoint'а явно этого не требует.
- Используй константы `Response::HTTP_*` вместо raw status numbers.
- Тело запроса должно маппиться в DTO через `#[MapRequestPayload]` или `Dto::fromArray($request->toArray())`.
- Service должен возвращать DTO, а не Entity.
- Reference controllers/endpoints должны отдавать только справочные данные; бизнес-логику и тяжёлые профильные queries выноси в профильные endpoints/services.

## DTO

- DTO должны быть pure data.
- Не используй `?? null` в `fromArray()`, чтобы скрыть отсутствие обязательных полей.
- Отсутствие обязательного input должно валидироваться или явно падать.

## Doctrine и миграции

- Doctrine migrations должны содержать только DDL: `CREATE`, `ALTER`, `DROP`, `INDEX`.
- `INSERT`, `UPDATE` и `DELETE` в migrations являются blockers, если MR явно не документирует принятый migration strategy.
- `up()` и `down()` должны быть симметричными, где это возможно.
- Foreign keys в Doctrine entities должны быть plain `int` columns, а не `ManyToOne` / `JoinColumn`, если затронутый проект не имеет другого явного соглашения.
- Новые MySQL таблицы и колонки должны использовать `utf8mb4_general_ci`, а не `utf8mb4_0900_ai_ci`, если проект явно не зафиксировал иной стандарт.
- Таблицам больше 1M строк нужна online migration strategy: `ALGORITHM=INPLACE, LOCK=NONE`, `pt-osc` или `gh-ost`.
- Для новых WHERE/JOIN путей нужны индексы в том же MR или documented existing index.

## SQL и data access

- SQL должен использовать prepared statements или Doctrine QueryBuilder.
- Флагай Cartesian joins, отсутствующие join predicates и разведочные queries без `LIMIT`.
- Флагай вероятный N+1 в loops, которые делают DB query на каждую строку.
- Bulk operations должны быть chunked, обычно по 500-1000 строк, с периодическим flush/clear при Doctrine.
- Для cross-db schema env вроде `DB_*_SCHEMA` не используй fallback на production/default schema; отсутствие env должно явно падать.
- В SQL предпочитай явно видимые table names вместо helper/autogenerated table name wrappers, если проектный стандарт не требует обратного.

## Frontend Vue

- Новые Vue components должны использовать `<script setup lang="ts">`.
- Новые или затронутые components должны объявлять `defineOptions({ name: 'ComponentName' })`, когда применяется текущий codeStyle.
- Имена файлов components должны быть PascalCase.
- Нельзя мутировать props напрямую.
- Нельзя мутировать Pinia store state из components; используй store actions.
- Избегай прямой работы с DOM через `document.*`.
- Не используй `v-html`.
- Forms должны использовать Vuelidate и PrimeVue `:invalid` для ошибок, если проект использует этот stack.

## TypeScript

- Не добавляй `any`; используй `unknown` плюс narrowing для неизвестных данных.
- Держи interfaces для store state, API responses и props.
- Предпочитай `I*` interfaces и `T*` type aliases там, где проект следует таким TypeScript rules; frontend type aliases должны именоваться с заглавной `T`.
- Не используй optional chaining как замену required business invariant. Сначала assert или throw.
- Для видимых пользователю enums/statuses держи одну label map рядом с const/union.
- Бизнес-значения статусов/типов на фронте держи в `as const` object/enum-like map, а не как разрозненные magic string/number literals.

## Frontend API layer

- Новые проекты должны использовать общий `ky` instance; legacy projects могут оставаться на общем axios.
- Не создавай несколько независимых HTTP clients с дублирующими hooks/interceptors.
- JWT refresh и authorization headers должны быть в API layer.
- HTTP errors должны пробрасываться вызывающему коду; не превращай failed responses в success.
- Global loading должен управляться через project API-layer flag/event pattern, а не прямую DOM-мутацию.

## Security

- Sensitive endpoints требуют явной авторизации: `#[IsGranted]`, `denyAccessUnlessGranted`, passport/JWT validation или project equivalent.
- Не логируй PII, JWT, passwords, tokens, email, phone или full names.
- Secrets должны оставаться в env/Symfony secrets, а не в code.
- Runtime endpoints, DSN, RabbitMQ/AMQP hosts, credentials, service URLs и project-local absolute config должны жить в `.env`, env vars или secrets, а не быть захардкожены в service code или committed config.
- Public endpoints должны иметь rate limiting, если затронутая область exposed externally.
- Не добавляй public/internal HTTP endpoints для действий, которые по архитектуре должны идти через message bus/pub-sub, если нет явной авторизации и причины отхода от event flow.

## Events и messaging

- Если MR затрагивает проект с уже принятым event client/package, используй этот клиент; не дублируй publisher/client в каждом сервисе.
- В event contract payload должен содержать устойчивый факт и identifiers; display-only, derived и mutable поля потребитель должен получать сам по id.
- Для internal notifications/events следуй принятому в проекте transport/message bus/pub-sub flow; прямой HTTP endpoint требует явной причины и авторизации.
- Если изменение данных и audit/log write должны быть согласованы, выполняй их в одной transaction.

## Dependencies и generated files

- Не коммить project-local Composer `repositories` с `type: vcs`/`path` на временные, экспериментальные или соседние репозитории, если MR не является инфраструктурным изменением dependency source.
- В `composer.json` не задавай ручную `version` для приложения/пакета, пока соответствующий Git tag не запушен и MR не меняет release metadata.
- Generated, reference, local runtime или machine-specific config файлы должны быть удалены из репозитория и добавлены в `.gitignore`, если они не являются поддерживаемым source artifact.
- Текстовые файлы должны заканчиваться newline; флагай `\ No newline at end of file` как `NIT`, если diff показывает рукописный файл.

## Tests

- Новый behavior должен иметь focused tests.
- API changes требуют хотя бы один happy path и один edge/error path, когда это практично.
- Избегай DB mocks для поведения, которое в проектах стека должно проверяться integration tests.
- Если CI red или skipped, нужен явно documented reason перед deploy.
